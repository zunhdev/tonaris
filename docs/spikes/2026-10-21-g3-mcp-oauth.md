# Tonaris — G3: MCP SDK v2 and Better Auth OAuth in Claude web, ChatGPT web and Codex, 21 October 2026

Spike for [TON-22](https://linear.app/zunhdev/issue/TON-22), the first half of G3 ([PRD §8](../product-requirements.md)). It checks the MCP server of [TS-60](../tech-spec.md) and the OAuth 2.1 authorization of TS-61 in the three required clients:

- MCP SDK v2 (`@modelcontextprotocol/server` 2.3.1), with the stateless fallback for 2025-era clients on;
- Better Auth 1.7.12 as the authorization server: `@better-auth/mcp`, `@better-auth/cimd` and `jwt()`;
- Client ID Metadata Documents (CIMD), with DCR as the fallback;
- RFC 9728 resource metadata, tokens bound to `/mcp`, and a consent page offering Read-only or Manage collection;
- revocation.

Approvals, write tools and ChatGPT's write actions are [TON-23](https://linear.app/zunhdev/issue/TON-23), the second half of G3.

## Verdict

**Go. All three clients connect, list the tools and call the read tools, and revocation takes effect on their next call.** The stack in TS-60 and TS-61 works as specified, with the refinements below. The code stays as the base for M9.

| Check (TON-22 "done when") | Claude web | ChatGPT web (Plus) | Codex (CLI 0.162.1) |
| --- | --- | --- | --- |
| How the client registered | CIMD `https://claude.ai/oauth/mcp-oauth-client-metadata`, public client | CIMD `https://chatgpt.com/oauth/client.json`, authenticating with `private_key_jwt` | CIMD `https://chatgpt.com/oauth/codex/client.json`, native public client, loopback redirect |
| Sign-in and consent | Passed | Passed | Passed |
| Protocol revision | 2026-07-28 (`server/discover`), and 2025-11-25 `initialize` after a reconnect | 2026-07-28 | 2025 handshake, through the stateless fallback |
| Lists tools; calls `get_overview` and `search` | Passed | Passed | Passed |
| Refresh token | Yes | **No**: it doesn't ask for `offline_access` (finding 11) | Yes |
| Revocation | Next call 401 within 18 s, refresh refused, "Reconnect a connector to keep using it" | Next call 401, then sign-in and reconnect | Not tried live; covered by the tests |

All live connections used **Manage collection**, the creator's choice. **Read-only** was checked by the automated tests, from the consent page through the tools.

**Still open:** ChatGPT's refresh token (finding 11); last-used times for Settings (DS-86); the DCR limit's value, which is a proposal. See [Open](#open).

## Findings

### Discovery and registration

1. **Discovery works as TS-61 describes.** Every client sent a request without a token, followed the 401's `resource_metadata` to `/.well-known/oauth-protected-resource/mcp`, then read the authorization server's metadata.
   - Better Auth's issuer is `https://api.<host>/auth`, so RFC 8414 puts the metadata at `/.well-known/oauth-authorization-server/auth`. All three clients used that path.
   - The root `/.well-known/oauth-authorization-server` is served too, for 2025-03-26 clients.
   - ChatGPT also tries three OpenID Connect discovery paths. They answer 404, which is right, since Tonaris isn't an OpenID provider.
2. **All three clients registered by CIMD. None used DCR.**
   - The documents are fetched by `@better-auth/cimd`'s transport. It resolves the host once, refuses private addresses and pins the connection. Bun honours the `lookup` override it relies on (checked against a black-hole address).
   - Fetches of the documents time out and cap the body size, and fetches of a client's JWKS time out after 5 s.
   - DCR stays on as the fallback, limited to **10 registrations per IP an hour**. Claude and ChatGPT call from shared address ranges, so a per-IP limit would throttle their users together. They don't use DCR, though.
3. **ChatGPT authenticates at the token endpoint with `private_key_jwt`.** Its document names `token_endpoint_auth_method: private_key_jwt`, with keys at `https://chatgpt.com/oauth/jwks.json`.
   - TS-61 assumed `none`. Better Auth advertises and verifies both, and records each assertion so it can't be replayed (`oauth_client_assertion`).
   - The token exchange, signature check included, took 132–138 ms.
4. **Claude's document also declares the `jwt-bearer` grant**, which is for its Enterprise Managed Auth. Tonaris doesn't offer that grant, and the normal flow is unaffected.
5. **Codex redirects to `http://127.0.0.1:<random port>/callback`.** Better Auth accepts any port on a loopback redirect for a client declared `native`, which Codex's document is.

### Protocol and tools

6. **The stateless fallback is needed.**
   - Claude and ChatGPT speak 2026-07-28: `server/discover`, then `tools/list` and `tools/call`.
   - Codex 0.162.1 still uses the 2025 handshake (`initialize`, then the `initialized` notification, answered 202).
   - After reconnecting, Claude used a 2025-11-25 `initialize` too.

   Keep `legacy: "stateless"` (TS-60). Better Auth's README recommends `legacy: "reject"`; ignore that, as TS-60 already says.
7. **Responses are single JSON bodies.**
   - The handler's default `auto` mode streams only when a tool sends notifications, and these tools send none. So the quick tunnel's lack of SSE support didn't matter.
   - `responseMode: "json"` logs a warning on every request, so the default stays.
8. **Tool calls took 3–62 ms at the server.** Token requests took 9–178 ms, well inside Claude's 10 s limit for OAuth endpoints. ChatGPT's tool calls arrive from `openai-mcp/1.0.0 (Codex)`, so ChatGPT web runs MCP through Codex's client.

### Modes, consent and revocation

9. **A mode is stored as scopes:** `collection:read` for Read-only, and `collection:manage` as well for Manage collection.
   - The consent page grants the subset the person chose, and Better Auth refuses to grant a scope the client didn't ask for. So Manage can only be granted to a client that asked for `collection:manage`.
   - The 401 challenge and the resource metadata name both scopes, and all three clients asked for both.
   - TS-61's "whatever scopes were requested" therefore means: Read-only is always available, and Manage only when it was asked for. The page offers only what can be granted, and says so when neither can.
10. **A connection is Better Auth's consent: one per person and client.**
    - Authorizing again within an existing consent skips the consent page. Codex's second login went straight to its callback.
    - `prompt=consent` shows the page again. If the person then narrows the mode, the connection's scopes cap tokens issued earlier, because the mode is what both the connection and the token grant (TS-62).
    - One consequence: claude.ai on the web, Desktop and mobile share one client, so they share one Tonaris connection.
11. **Refresh tokens need `offline_access`.**
    - Better Auth leaves it out of the resource metadata, since it is an authorization-server scope.
    - Claude appends it, and Codex takes it from the authorization server's metadata. ChatGPT asked only for the two mode scopes, so **it got no refresh token** and would have to sign in again after an hour.
    - The 401 challenge now names `offline_access` too.
    - ChatGPT saved its scopes when the plugin was created and didn't run discovery again when reconnecting. So the fix can only be confirmed with a fresh plugin, which TON-23 sets up anyway.
12. **Revocation is immediate, although access tokens are JWTs that live an hour.**
    - Every MCP call checks that the token's connection still exists, with one indexed query, and takes the mode from it.
    - Revoking deletes the consent and the client's tokens for that person.
    - Claude's next call failed 18 s after the revoke, its refresh token was refused, and it asked to reconnect. ChatGPT's next call failed, and it sent the person through sign-in again.

### Better Auth on our stack

13. **`requireMcpAuth` fetches the JWKS over HTTP from the API's own public URL.** In tests nothing listens there, and in production it would be a needless round trip through the host's proxy.
    - The API verifies tokens in-process instead, with Better Auth's own pieces: `verifyJwsAccessToken` with the keys from `auth.api.getJwks()`, `enforceDpopBinding`, and `createResourceServerChallenge` for the 401.
    - Signature, issuer, audience `/mcp`, expiry, `azp` and a DPoP binding are all checked, as `requireMcpAuth` checks them.
14. **The OAuth provider writes its resource row while Better Auth starts.** Any process that creates the auth therefore touches the database:
    - the OpenAPI generator never exited;
    - tests that finished quickly dropped their schema under the write.

    The generator and the plain app test now keep Better Auth's rows in memory (`db: "in-memory"`), and test apps wait for start-up to finish.
15. **The JWT plugin has an endpoint that signs a session (`/auth/token`).** It isn't served, because the `/auth` allowlist leaves it out. Its `set-auth-jwt` header on session reads is switched off.
16. **Sign-in continues the authorization without carrying Better Auth's signed query.** The signed query lasts 10 minutes, and the emailed-code flow can take longer.
    - Signing in returns to `/oauth/authorize` with the client's original request. The API runs it again with the new session, then signs a fresh query for the consent page.
    - `prompt=login` is dropped then, because signing in just satisfied it.

### Security and HTTP details

17. **The CSRF rule needed two refinements.**
    - The token and revocation endpoints take form posts and never read the session, so they are exempt.
    - Only POST must carry JSON. Browsers always preflight a cross-origin DELETE, PATCH or PUT, so a DELETE with no body passes. The cookie and origin rule still applies to all of them.
18. **An empty 204 in Elysia needs `z.null().optional()`.** Elysia validates the absent body as `undefined`. `z.void()` can't be put in the OpenAPI document. A route's `detail.responses` is ignored once it declares `response`.

### ChatGPT on a personal plan

19. **ChatGPT Plus can add a custom MCP server, on the web.**
    - The path is `chatgpt.com/plugins` → **Add** → create an MCP app with the server URL and OAuth.
    - No Developer mode toggle was needed, and none was found under Settings → Security and login.
    - The two read tools worked. Whether Plus allows write actions, and how it confirms them, is TON-23's check (TS-123's open question).

## Open

- **ChatGPT's refresh token.** Confirm with a fresh plugin that the challenge's `offline_access` gives ChatGPT a refresh token (TON-23). If it doesn't, ChatGPT users sign in again every hour.
- **Read-only, live.** No live client used Read-only; the tests cover it. TON-23's script consents in each mode.
- **Last used** (DS-86) needs a column of our own, updated when a token is used (M9).
- **The DCR limit** of 10 per IP per hour is a proposal for the creator.
- **Browser-based MCP clients** would need CORS on `/mcp` and the token endpoint. None of the required clients is one.

## Running it again

The clients reach the API over the internet, so the spike runs both services behind one cloudflared quick tunnel. One origin keeps a host-only session cookie that both see; production keeps two hosts (TS-08).

1. `brew install cloudflared`, `bun run db:migrate`, and `bun run build` in `apps/web`.
2. `cloudflared tunnel --url http://localhost:8787`. It prints `https://<name>.trycloudflare.com`, which is `$T` below.
3. `bun tooling/src/mcp-verification/tunnel-proxy.ts`.
4. In `apps/api`: `API_ORIGIN=$T WEB_ORIGIN=$T CLIENT_IP_HEADER=cf-connecting-ip bun src/index.ts`.
5. In `apps/web`: `API_URL=$T bun run start`.
6. Connect each client to `$T/mcp`:
   - **Claude:** Settings → Connectors → Add custom connector.
   - **ChatGPT:** `chatgpt.com/plugins` → Add.
   - **Codex:** `codex mcp add <name> --url $T/mcp`, then `codex mcp login <name>`.

   Sign-in codes go to Mailpit (http://localhost:8025). `workload@tonaris.test` has 5,000 albums.

Caveats:
- The quick-tunnel API timed out on some attempts, so retry.
- macOS caches a lookup of the new host made before it resolves, for 60 s.
- The proxy logs each MCP request's method and protocol revision.
